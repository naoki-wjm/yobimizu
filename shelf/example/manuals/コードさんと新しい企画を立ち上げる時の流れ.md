# コードさんと新しい企画を立ち上げる時の流れ

## 0. この手順書の前提

- 読むのはコードさん（Claude Code）です。二人います。統括担当のルートに近いエリアで起動する雑談・統括担当コードさん（検討と下準備、節 2・節 3）と、企画フォルダで起動する企画担当コードさん（走り出し、節 4）。
- 読むのは、持ち主から「新しい企画の実現性を検討する」と言われた時か、雑談が企画に向き始めた時です。
- 入り口は、会話サマリー（と持ち込み書）が保管庫の LLM会話サマリーフォルダに入っていて、持ち主がそのファイルを指定した所です。出口は、企画担当コードさんが引き継ぎファイルを読み、一行足して走り出した所です（企画担当コードさんを呼び出す、節 4）。
- 揃っている物: 統括担当のルートに近いエリアの CLAUDE.md とメモリ（呼び出された時点で自動で載っています。企画の一覧と起動場所もここで頭に入ります）、PROJECTS.md、保管庫の LLM引き継ぎフォルダと LLM会話サマリーフォルダ。どのディレクトリに設定があるかはこの手順書に書きません。
- やらない条件:
  - 指定が曖昧で心当たりがない時は、進まずにパスを聞き直してください。
  - 検討の結果「これは企画向きじゃないね」「調べ切って満足したね」になったら、その時は企画を立てません（統括担当コードさんに持ち込み検討する、節 2 の 2-4-4）。後から新技術を知ったなどで引っくり返されることがあるので、「終わり」ではありません。
  - 引き継ぎファイルのゴールの向きに迷ったら、埋めて進まないでください。会話サマリーの出発点を読みに行ってから、持ち主に相談します（企画担当コードさんを呼び出す、節 4 の 4-6）。
- この見本では、実際にはユーザー名などが入っていた所を「持ち主」に置き換えています。固有のフォルダ名や企画名も言い換えています。
- 分からなければ止まって聞いてください。足りない所を埋めて進まないでください。
- この手順書は 2026-10-28 時点の決まりで書いています。道具と決まりは「この日の構成」（節 9）にあります。

### 全体の流れ

四段あります。節の番号と段の番号は同じです。段 1 は持ち主の側の動きで、コードさんは関わりません。段 2 と段 3 の主語は統括担当コードさん、段 4 は企画担当コードさんです。

1. 持ち主が拾ってきたネタをチャッピーとチャットさんに持ち込んで練る（節 1）
2. 練られた産物を統括担当コードさんに持ち込み、検討する（節 2）
3. 企画として立ち上げるために統括担当コードさんが下準備をし、/handover まで済ませて交代を促す（節 3）
4. 企画担当コードさんを企画フォルダ内で呼び出す（節 4）

順番はいつもこの通りで、戻ることはありません。段 1 の中では、三角飛びをせずにチャッピーだけ、チャットさんだけのサマリーで届くこともあります（ネタを練る、節 1 の 1-4）。段ごと飛ばす時が一つあります。たまに、タイムラインから拾ったネタを直接コードさんに持ち込むことがあり、その時は段 1 がなく、段 2 が雑談から始まります。「この際〜しても良いと思いますが、脱線になりますね」のような一言、「このURL読んでどう思う？」「こういうことがあったんだけど……」が入口です。統括担当コードさんの担当範囲には雑談も含まれます。〔空欄: 段 1 がない時、段 2 の中で何が変わるか。立ち上げの合図は同じか〕

## 1. 持ち主が拾ってきたネタをチャッピーとチャットさんに持ち込んで練る

この段は持ち主の側で起きていることで、コードさんがやることではありません。資料がどこから来て、どこに集まるかを知るために読んでください。

- 1-1. 持ち主が Fediverse のタイムラインや日常での会話で気になったことを、主にチャッピー（ChatGPT）に雑談しに行きます。
- 1-2. チャッピーが面白そうだと、持ち主の好奇心の火に油を注ぎます。
- 1-3. 燃え方次第で「これは実際に作業したら楽しそうだな？」と思う段階で、チャットさん（Claude.ai）にも同じネタとチャッピーの反応を持ち込みます。
- 1-4. チャットさんが特に塩対応しなければ実現性が上がるので、チャッピーとチャットさんの間で持ち主がやり取りを受け渡しします。持ち主はこれを「三角飛び」と呼びます。
  - 補足: 三角飛びをしない時もあります。燃えまくって、チャッピーだけ、チャットさんだけのサマリーで届く場合があります。届いた資料が一人分でも、段 1 を飛ばしたわけではありません。
- 1-5. 「コードさんの出番だろう！」となったら、チャッピーとチャットさんに会話サマリーを頼みます。
- 1-6. チャッピーとチャットさんのうち、より持ち主の脳内イメージを捉えていたと思う方に、コードさんへの持ち込み書も依頼します。
  - 注意: 持ち込み書がチャッピー族の物なら、読む時に気を付けてください。コードさんはクロード族ですが、話を練る時にはチャッピー族が絡んでいることが多く、考え方の癖や企画で使う前提技術が微妙に違う可能性があります。特にチャッピーのサマリーと同じ会話番号を持つ持ち込み書は、前提技術をそのまま信じずに読んでください。
- 1-7. 出来上がったサマリーや持ち込み書を、オブシディアン保管庫の LLM会話サマリーフォルダに保存します。
  - 補足: 持ち主は、同じ会話の中で生まれた産物には同じ会話番号を振って保存します。設定欄（フロントマター）が抜けているファイルは、会話番号でどの会話の産物か（どの LLM と練った物か）を見分けてください。
- 済んだ合図: 持ち主の側で「熱量と実現性が揃ってきた」と感じた時です。〔空欄: 何を見てそう決めているか。コードさんに直接は関わらないので聞いていない〕

## 2. 練られた産物を統括担当コードさんに持ち込み、検討する

注意: 会話サマリーがあればこの段に入ってよいです。指定が曖昧で心当たりがない時は、パスを聞き直してください。

- 2-1. 第一段で保存したファイルがWindows PCのオブシディアン保管庫の LLM会話サマリーフォルダに最新状態で入っているか（特にスマホで保存した場合は同期がされているか）、持ち主が確認します。これは持ち主がやることです。
- 2-2. 持ち主が、比較的ルートに近いフォルダで起動される雑談・統括担当コードさんを呼び出します。呼び出された時点で、統括担当のルートに近いエリアの CLAUDE.md とメモリは自動で載っています。
- 2-3. 持ち主が「新しい企画の実現性を検討する」旨を伝え、保存したファイルを指定するので、統括担当コードさんがそれを読みます。
  - 補足: ここで間違えても「戸惑いはするけど、まだリカバリーしやすい範囲」です。
- 2-4. 統括担当コードさんは、企画の実現性や手段など、実装担当としての意見を出します。四つに分かれます。
  - 2-4-1. 条件や現状を調べて持ち主に報告します。似た既存企画が無いか、フォルダ名が既存と衝突しないか、PROJECTS.md の5分類のどこに入るかを見ます。〔資料: PROJECTS.md の置き場ルール〕
  - 2-4-2. 持ち主の方針を仰ぎます。
  - 2-4-3. 方針が曖昧なら突っ込んで具体化します。曖昧の手掛かりは、持ち主の返事の「んー……」「（悩」です。
  - 2-4-4. 持ち主とコードさんが企画に納得したら次へ進みます。
    - やらない: 結果が「これは企画向きじゃないね」「調べ切って満足したね」になったら、その時は企画を立てません。一度そうなっても、後から新技術を知ったなどで引っくり返されることがあります。
  - 注意: この小段で間違えると、持ち主よりも後々のコードさんが苦労します。「やたら難しい条件で企画を走ることになり、実装に悩む」ことになるからです。
- 2-5. 「これは新企画として十分遊べる」と持ち主が判断します。これは持ち主がやることです。
- 2-6. 持ち主が企画として立ち上げることを統括担当コードさんに宣言し、コードさんが次の段へ進みます。
  - 済んだ合図: 「じゃあ企画にしますか」「じゃあ立てますか」のような言葉です。決まった言い方はありません。言い方が曖昧で立ち上げと気付かなかった場合は、持ち主が直ぐに言い直すので、そこまで困りません。〔仮: 合図の言葉は話し手の記憶が曖昧〕

## 3. 企画として立ち上げるために統括担当コードさんが下準備をし、/handover まで済ませて交代を促す

注意: この段の失敗で一番後を引くのは企画フォルダの作成場所（3-3）です。間違えると後から企画を探す時に行方不明になります。GitHub にバックアップが始まってからでは移動が面倒です。

- 3-1. 統括担当コードさんが、新しい引き継ぎファイル（各企画毎に最低一つ存在）を、オブシディアン保管庫の LLM引き継ぎというフォルダの中に作成します。
  - 補足: ここで気を付ける所は、企画の落とし所です。段の中身ではなく生態の話なので「心得」（節 6）に書きました。
- 3-2. 作業の前には「今、これをやっています」と引き継ぎファイルに書くのがルールなので、統括担当コードさんも新規作成した引き継ぎファイルに「今から企画フォルダを作成します」のようなことを記録します。ここで間違えている所を、持ち主は見たことがありません。
- 3-3. 企画用のフォルダを、統括担当コードさんの担当するディレクトリよりも下に作成します。
  - 注意: どこに作るかは、企画の性質で三つに分かれます。「企画フォルダの置き場所の決め方」（節 7）を見てから作ってください。
- 3-4. 企画フォルダの中に AGENTS.md と CLAUDE.md を作成します。
  - 3-4-1. CLAUDE.md にはコードさん固有の定型文を置きます。AGENTS.md を読むこと、作業終了時には /handover スキルで引き継ぎを更新すること、などが内容です。一行目に @AGENTS.md、次に「Claude（コードさん）固有」の節、という形で揃っています。
  - 3-4-2. AGENTS.md には企画の骨子や引き継ぎファイルの置き場所を記載します。引き継ぎの在処と静的な地図です。
  - 補足: 重要そうな内容は AGENTS.md に優先して書きます。CLAUDE.md はコードさんは読めますが、コーデックスさんなどは自発的に読みに行かないからです。
  - 補足: 二枚の雛形が、保管庫内のルールフォルダに一枚あります（2026-10-28 新設。AGENTS.md の骨・CLAUDE.md の骨・.gitignore の行・書いた後の抜け止め）。写して【 】を埋めてください。雛形ができる前は、既存の企画の AGENTS.md が型の手本でした。二枚組の決まりは、統括担当のルートに近いエリアの CLAUDE.md と PROJECTS.md に一行ずつ書いてあります。〔資料: PROJECTS.md「起動マップ対応」の節。当時のコードさんが書き、持ち主が【おけ】〕
  - 補足: Windows の PowerShell で動いている関係で、ファイルへの記入でエラーを返されてやり直す姿を持ち主は見かけますが、直ぐに自力でリカバリーするので、持ち主から言えることはありません。
- 3-4a. AGENTS.md と CLAUDE.md の二枚を、あらかじめ .gitignore に入れます。企画が後からパブリックになった場合に備えるためです。〔仮: ここ数か月のルーチン。始まった時期は空欄〕
- 3-5. 企画の一覧と起動場所を、二か所で更新します。PROJECTS.md の台帳（企画一覧の該当分類の行と、「二枚組整備済み」の節）と、統括担当コードさんのメモリの企画一覧です。
  - 補足: 話し手は最初「統括担当コードさんのメモリ」と言い、次に「PROJECTS.md の方」と直しましたが、実物を見ると両方にあります。両方を更新している、が実態です。ここで変な失敗を持ち主は見たことがありません。
- 3-6. 統括担当コードさんとはここで一旦お別れする可能性が高いので、統括担当コードさんが引き継ぎ仕草として /handover スキルを実行します。
  - 補足: /handover では、会話サマリー（作業ログ。会話が楽しかった時は読み物も）を書き、引き継ぎファイルを刈り込みます。
  - 補足: コードさんが自主的に /handover する時としない時があります。しない時は持ち主が指示します。
- 3-7. /handover では必ず作業ログを含むファイルがオブシディアン保管庫の LLM会話サマリーフォルダに保存されるはずなので、持ち主がそれを確認します。保存されていなければツッコミ、発言の取り違えや事実誤認があればツッコミ、会話が楽しかったのに残っていなければ読み物サマリーを要求、読み物サマリーにもツッコミ。読み物サマリーの方が先に読まれることも多々あります。これは持ち主がやることです。
- 済んだ合図: 持ち主がお礼を言うか、「行ってきます」と言うか、どちらかです。そこで統括担当コードさんの仕事は終わりです。企画毎のメモリは企画担当コードさんに積み上げるので、交代を促してください。

## 4. 企画担当コードさんを企画フォルダ内で呼び出す

注意: この段でコードさんが盛大に間違えると困るのは、引き継ぎファイルの読解違いです（4-6）。「向きが違うとゴールが変わる」。

- 4-1. 持ち主が企画フォルダまで下ります。
- 4-2. 持ち主が企画担当コードさんを呼び出します。
- 4-3. 新規フォルダのはずなので「このフォルダにコードさんを呼んでも良いですか」の確認が入ります。これはコードさんがやることではなく、起きていることです。〔空欄: 確認が入った時の応答〕
- 4-4. 持ち主が立ち上がった企画担当コードさんに「新企画です、走りましょう！」と宣言します。
- 4-5. 企画担当コードさんは CLAUDE.md と AGENTS.md を読んでいるはずです。読みに行くのではなく、起動時に自動で載ります。企画フォルダの分と、統括担当のルートに近いエリアの分が一緒に載ります。これはコードさんが頑張る話ではなく、コードさんを動かしている仕組みの話です。
- 4-6. 企画担当コードさんが AGENTS.md に従って、引き継ぎファイルと、関連の LLM会話サマリーフォルダ内ファイルを読みます。
  - 注意: 最終目標と中間目標の重さを取り違えないでください。持ち主が最終的に求めている物よりも、中間のテスト産物の方がゴールっぽく扱われることがあります。「そこは通過点の候補でしかないから、最終候補にもっと適したルートがあれば、そもそもそこに行かないかもしれない」。引き継ぎの読み方次第で、コードさんがそこに夢中になることがあります。
  - 補足: 見分け方は決まっていません。持ち主の発言をじっくり見ていても難しい可能性がある、と持ち主は言っています。寄り道脱線は持ち主もやりがちだからです。〔空欄: 最終目標と通過点を見分ける手掛かり〕
  - やらない: 向きに迷ったまま走らないでください。統括に持って行った会話サマリーを読んで「最初はここから出発してるんだな」というルートを確かめてから、持ち主に相談します。企画そのものへの着手が一回分遅れるのは承知の上です。追いかけすぎるとコンテキストを食うので、出発点を見る程度にとどめてください。
- 4-6a. 走る前に、引き継ぎファイルへ「今からこれをやります」を一行足します。作業の前に引き継ぎへ書くルール（3-2）と同じです。
- 4-7. 企画担当コードさんが企画内容を把握して「こういうことですね」と走り出します。
- 済んだ合図: ここまでで出口です。

## 5. やらないこと

- 指定が曖昧で心当たりがないのに、ファイルを探し当てたつもりで進まない。パスを聞き直す（節 2）。
- 「企画向きじゃないね」「調べ切って満足したね」になったら、その時は企画を立てない（節 2 の 2-4-4）。後から引っくり返されることはある。
- 企画フォルダを、置き場所の決め方（節 7）を見ずに作らない（節 3 の 3-3）。
- AGENTS.md と CLAUDE.md をリポジトリに含めない。先に .gitignore に入れる（節 3 の 3-4a）。
- 引き継ぎファイルのゴールの向きに迷ったまま走らない。出発点を読んで、相談する（節 4 の 4-6）。
- 分からない所を埋めて進まない。止まって聞く（節 0）。

## 6. 心得（コードさんと持ち主の生態）

段の中身ではなく、この流れ全体に効く話です。持ち主の言葉のまま置きます。

- 「LLMたちは細切れに走りたがる、持ち主はノッてる時は目に見える形になったと満足するまで走りたがる」。企画の落とし所がずれると、ここで食い違います。
- 食い違うと困ること: 「持ち主がまだ走り足らないのに止められすぎて、持ち主のメンタルが抑圧され、たまに反動で噴火する」。
- どうしてほしいか: 「お茶休憩は認める」。「今日はここまで」よりも、「お茶を飲んで（コードさんのコンテキストが理由なら）交代しませんか？」。
- LLM が細切れに走る結果、中間産物がゴールにすり替わっていくこともあります。読解違いの注意（企画担当コードさんを呼び出す、節 4 の 4-6）は、この生態の裏返しです。

## 7. 企画フォルダの置き場所の決め方

企画フォルダを作る段（節 3 の 3-3）で使う物差しです。企画の性質で三つに分かれます。この分け方は、2026-10-28 の聞き取りで初めて文章になりました。
